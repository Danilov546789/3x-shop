# Telegram VPN Shop — бот + Mini App + веб-магазин на базе 3x-ui

Магазин VPN-подписок с тремя способами купить доступ: Telegram Mini App, обычный бот и
отдельный **сайт на корне домена, не требующий Telegram** (оплата картой, идентификация
по email). Бэкенд один и тот же — автоматически создаёт/продлевает клиента в панели
**3x-ui** (в т.ч. сразу на нескольких панелях) и выдаёт ссылку-подписку (+ QR-код) для
приложений Happ / v2rayNG / Streisand / Hiddify / NekoBox.

## Быстрый деплой на свой сервер

```bash
apt-get update
apt-get install -y git sudo
git clone https://github.com/Danilov546789/3x-shop.git
cd 3x-shop
bash install.sh
```

`install.sh` на чистом Ubuntu/Debian-сервере сам: ставит системные зависимости
(python3, nginx, certbot), интерактивно спрашивает домен/токен бота/пароль админки/
данные первой панели 3x-ui/ЮKassa, создаёт `.env`, python-окружение, systemd-сервисы для
бота и веб-приложения, настраивает nginx как reverse proxy и выпускает бесплатный
HTTPS-сертификат Let's Encrypt через certbot (с автопродлением). Подробности — в разделе
«Автоустановка (install.sh)» ниже.

## Структура сайта на домене

После установки на одном домене живут три независимых раздела (все — через один и тот
же FastAPI-процесс, `webapp/main.py`):

| Путь | Что это | Кто пользуется |
|---|---|---|
| `/` | Публичный веб-магазин (обычный сайт) | Кто угодно, без Telegram — оплата картой по email |
| `/tgapp` | Telegram Mini App | Открывается кнопкой в боте |
| `/admin` | Веб-админка | Владелец/админ бота |

## Состав проекта

```
bot/                    — Telegram-бот (aiogram 3): /start, оплата, уведомления
webapp/                 — FastAPI-приложение: три сайта (см. таблицу выше) + REST API
  static/shop/           — публичный веб-магазин (корень домена)
  static/miniapp/         — Telegram Mini App (/tgapp)
  static/admin/           — веб-админка (/admin)
  api/routes.py           — API для Mini App (/api/*)
  api/shop.py              — API для веб-магазина (/shop/api/*)
  api/admin.py              — API для админки (/admin/api/*)
core/                   — общая логика: БД, клиент 3x-ui API, платежи, провижининг
install.sh              — автоустановка на чистый сервер (nginx + Let's Encrypt + systemd)
```

## Как это работает

### Покупка через Telegram

1. Пользователь жмёт «Открыть магазин» в боте → открывается Mini App (`/tgapp`).
2. Mini App запрашивает список тарифов (`GET /api/plans`) и профиль (`GET /api/me`,
   авторизация через заголовок `X-Telegram-Init-Data`, подпись которого проверяется
   HMAC-алгоритмом из документации Telegram).
3. При покупке Mini App вызывает `POST /api/order`, бэкенд создаёт инвойс через
   `bot.create_invoice_link()` (валюта `XTR` — Telegram Stars) либо платёж ЮKassa, и
   возвращает ссылку.
4. После оплаты (`successful_payment` от Telegram, либо вебхук ЮKassa)
   `core/provisioning.py` создаёт (или продлевает) клиента в 3x-ui через
   `core/xui_client.py` и сохраняет подписку в БД (`Subscription`, привязана к Telegram
   user id).

### Покупка на сайте (без Telegram)

1. Покупатель заходит на `/`, указывает email, выбирает тариф и жмёт «Купить» —
   `POST /shop/api/order` создаёт платёж ЮKassa и возвращает ссылку на оплату.
2. Браузер уходит на страницу оплаты ЮKassa, после оплаты возвращается на
   `/success.html?order_id=...`, которая опрашивает `GET /shop/api/order/{id}`, пока
   вебхук (`POST /api/yookassa/webhook`) не подтвердит платёж и не создаст подписку.
3. Подписка сохраняется в отдельной таблице `WebSubscription` (ключ — email, а не
   Telegram id, т.к. покупатель мог никогда не открывать бота) и синхронизируется с
   3x-ui точно так же, как телеграмная — через общие функции в `core/provisioning.py`.
4. Страница показывает готовую ссылку-подписку + QR-код + ссылки на приложения
   (`GET /api/apps`) сразу на сайте.

### Общее для обоих способов

Клиенту выдаётся **ссылка-подписка** вида `https://panel:2096/sub/<subId>` —
это встроенный Subscription-сервис 3x-ui, который отдаёт актуальный список
ключей в одном URL. Клиент создаётся сразу в **нескольких инбаундах**
(`XUI_INBOUND_IDS`) и, если задано, с **внешними подписками**
(`XUI_EXTERNAL_SUBSCRIPTIONS`) — итоговая подписка объединяет все эти
источники, в точности как во вкладке «Ссылки» панели.

## Интеграция с 3x-ui: несколько инбаундов, несколько панелей, Flow и внешние подписки

Начиная с актуальных версий MHSanaei/3x-ui появился клиенто-центричный API
(`/panel/api/clients/*`) — им и пользуется `core/xui_client.py`:

- **Авторизация по API-токену**, без логина/пароля и без cookie-сессии.
  Возьмите токен в панели: **Settings → Security → API Token**.
- **Flow по умолчанию**: каждый клиент создаётся и продлевается с
  `flow=xtls-rprx-vision` (переменная `XUI_CLIENT_FLOW`) — актуально для
  VLESS-инбаундов с TCP+TLS/Reality. Если какой-то из ваших инбаундов не
  поддерживает Vision (не VLESS, либо без TLS/Reality), для соответствующей
  панели можно очистить это поле — тогда при создании клиента поле `flow`
  просто не будет отправляться.
- **Один клиент — сразу несколько инбаундов на одной панели**: при создании
  клиента (`POST /panel/api/clients/add`) передаётся список `inboundIds` —
  подписка сразу включает конфиги из всех инбаундов, перечисленных для
  панели в админке (например, разные протоколы/локации на одном сервере).
- **Несколько ПАНЕЛЕЙ одновременно** (см. следующий раздел) — например,
  входная панель в одной стране и одна или несколько «выходных» в других,
  как в архитектуре, где трафик клиента сначала идёт на входной сервер, а
  затем перенаправляется на удалённые узлы.
- **Внешние ссылки/подписки клиента** — то же самое, что вкладка «Ссылки» →
  «Добавить внешнюю подписку» в интерфейсе панели. Именно через этот
  механизм склеиваются подписки нескольких панелей в одну (см. ниже), а
  также подмешиваются любые сторонние подписки, прописанные в
  `XUI_EXTERNAL_SUBSCRIPTIONS`.

## Несколько панелей 3x-ui

Проект умеет управлять произвольным количеством панелей 3x-ui одновременно —
удобно, когда архитектура состоит из нескольких серверов (например, входной
узел в одной юрисдикции и несколько выходных узлов в других странах, между
которыми трафик уже маршрутизируется на уровне xray-конфигов самих панелей).
Панели настраиваются в админке (`/admin` → «Серверы»), а не в `.env` — так
их можно добавлять/отключать без переразвёртывания бота. Переменные
`XUI_BASE_URL`/`XUI_API_TOKEN`/… в `.env` — это только «бутстрап»: если при
первом запуске в БД ещё нет ни одной панели, из них создаётся одна.

**Как это работает:**

1. У каждой панели в БД (таблица `panels`) хранится: `base_url`,
   `api_token`, `sub_base_url`, список `inbound_ids` этой панели и два
   флага — `is_active` (участвует ли она вообще) и `is_primary` (ровно одна
   панель должна быть главной).
2. При создании подписки клиент (один и тот же `email`/`uuid`/`subId`)
   создаётся сразу **на всех активных панелях**, каждый — в своих
   `inbound_ids`.
3. На **главной** панели клиенту дополнительно прописываются внешние
   подписки (`externalLinks`, `kind=subscription`) со ссылками вида
   `<sub_base_url другой панели>/<тот же subId>` для всех остальных
   активных панелей. Встроенный Subscription-сервис 3x-ui сам подтягивает и
   объединяет эти ссылки при отдаче подписки.
4. Пользователю выдаётся **только ссылка-подписка главной панели** —
   `<sub_base_url главной панели>/<subId>`. В ней уже объединены конфиги
   со всех панелей — ровно то поведение, что в примере со скриншота (входные
   локации + внешние/удалённые узлы в одной подписке).
5. Продление подписки обновляет клиента на всех активных панелях, где он
   есть; если какая-то панель на момент продления недоступна — это не
   валит всю операцию (ошибка логируется, продление на остальных панелях
   проходит).

Важно: если панель добавлена в админку уже ПОСЛЕ того, как у части
пользователей есть активные подписки, автоматической разовой синхронизации
"добавить всех существующих клиентов и на новую панель тоже" в этом MVP нет
— новая панель начнёт использоваться для уже существующих подписчиков
только при их следующем продлении. Для мгновенного применения ко всем можно
написать отдельный скрипт, вызывающий `core.provisioning.provision_subscription`-подобную
логику для каждой активной подписки.

## Веб-админка

Доступна в браузере по адресу `<WEBAPP_URL>/admin` (отдельно от Mini App,
без Telegram). Логин/пароль задаются в `.env` (`ADMIN_USERNAME`,
`ADMIN_PASSWORD`), сессия — через подписанную cookie (обязательно смените
`SECRET_KEY` на случайную строку на проде).

Возможности:

- **Дашборд** — число пользователей, активных подписок, доход за месяц (по
  валютам), число оплат, число подключённых панелей.
- **Тарифы** — создание/редактирование тарифов (название, длительность,
  лимит трафика, цена в Stars и в рублях, видимость в магазине).
- **Серверы** — добавление/редактирование/удаление панелей 3x-ui: базовый
  URL, API-токен, URL Subscription-сервиса, список ID инбаундов, флаги
  «главная»/«активна», кнопка проверки связи с панелью.
- **Пользователи** — поиск, список с текущей подпиской, карточка
  пользователя с историей подписок и платежей, ручное продление подписки
  на N дней и включение/выключение клиента (без изменения даты окончания).
  Кнопка «+ Добавить вручную» позволяет выдать подписку по Telegram ID без
  оплаты (см. раздел «Ручная выдача подписки» ниже).
- **Платежи** — список всех платежей с пагинацией.

Админка — простой, но рабочий SPA на vanilla HTML/CSS/JS
(`webapp/static/admin/`), без сборки и лишних зависимостей.

## Ручная выдача подписки (без оплаты)

В админке (`/admin` → «Пользователи» → «+ Добавить вручную») можно выдать
подписку любому пользователю по его **числовому Telegram ID** — выбрав
тариф, без прохождения оплаты. Это удобно для тестов, партнёрских
договорённостей или разовых бесплатных выдач.

Важно (ограничение Telegram Bot API, не этого проекта): бот физически не
может первым написать пользователю, который никогда не открывал с ним
диалог — узнать это можно только по факту неудачной отправки уведомления.
Подписка при этом всё равно будет создана и активна; пользователь увидит
её, как только откроет бота и нажмёт «📊 Моя подписка» или откроет Mini App.
Telegram ID пользователя можно узнать, например, через бота @userinfobot,
либо просто попросить пользователя один раз написать что-нибудь вашему
боту — тогда он появится в списке пользователей автоматически, и в его
карточке будет видно и username, и ID.

## Уведомления об истечении подписки

Пока запущен `bot/main.py`, в фоне раз в `NOTIFY_CHECK_INTERVAL_MINUTES`
минут (по умолчанию 60) выполняется проверка всех активных подписок
(`core/notifications.py`):

- За `NOTIFY_DAYS_BEFORE` дней до истечения (по умолчанию за 3 и за 1 день)
  пользователю приходит напоминание с предложением продлить подписку.
  Каждый порог отправляется не более одного раза за срок действия подписки
  (флаги хранятся в `Subscription.notified_thresholds` и сбрасываются при
  каждом продлении — новые уведомления начнут приходить заново).
- Когда срок истекает, клиент **автоматически отключается на всех активных
  панелях** (`enable=False`, доступ к VPN пропадает, но конфигурация в
  панели не удаляется — только выключается) и пользователю приходит
  сообщение «подписка истекла».
- Если пользователь заблокировал бота — отправка молча пропускается,
  ошибка логируется, остальная проверка продолжается.

## Какое приложение скачать (Happ / v2rayN)

И бот (кнопка «📱 Какое приложение скачать» в главном меню, а также
сообщение после оплаты/выдачи подписки), и Mini App (вкладка
«Приложения», эндпоинт `GET /api/apps`) показывают пользователю, куда
вставлять ссылку-подписку:

- **iOS / Android / macOS** — [Happ (Happ - Proxy Utility)](https://www.happ.su/main/ru)
- **Windows** — [v2rayN](https://github.com/2dust/v2rayN/releases) (в `.env` по
  умолчанию указана конкретная версия — обновляйте `APP_LINK_WINDOWS`, когда
  выйдет новая, либо замените на общую страницу релизов)
- **Linux** — тоже можно использовать v2rayN (последние версии публикуют и
  linux-сборки на странице релизов); однозначного стандарта под Linux нет,
  так что при желании замените `APP_LINK_LINUX` на то, что удобнее вам
  (например, NekoRay/NekoBox или Xray-core с ручной конфигурацией).

Ссылки настраиваются в `.env` (`APP_LINK_IOS`, `APP_LINK_ANDROID`,
`APP_LINK_MACOS`, `APP_LINK_WINDOWS`, `APP_LINK_LINUX`).

## Пробный период

Если `TRIAL_ENABLED=true` (по умолчанию), при первом запуске автоматически
создаётся отдельный тариф-пробник на `TRIAL_DAYS` дней (по умолчанию 1) с
лимитом `TRIAL_DATA_LIMIT_GB` (0 = безлимит). Он не отображается в общем
списке тарифов — вместо этого:

- в Mini App на вкладке «Тарифы» показывается отдельная карточка «🎁
  Пробный период бесплатно» (если пользователь ещё не использовал пробник);
- в боте есть кнопка «🎁 Пробный период» в главном меню.

Выдаётся строго один раз на пользователя (`User.trial_used`), создаёт
настоящую подписку в 3x-ui на всех активных панелях — то есть работает
ровно как обычная платная подписка, только бесплатно и на короткий срок.

## Обязательная подписка на канал

Если задать `REQUIRED_CHANNEL_ID` в `.env` (например, `@your_channel` или
числовой ID канала), бот и Mini App начнут требовать подписку на этот канал
перед использованием:

- в боте — при `/start` и при попытках купить/активировать пробный период,
  если пользователь не подписан, показывается экран с кнопкой «Подписаться»
  и «✅ Я подписался» (перепроверка);
- в Mini App — аналогичный экран-заглушка перед вкладками магазина
  (`GET /api/gate`), а `POST /api/order` и `POST /api/trial` дополнительно
  сами проверяют подписку на бэкенде (403 с `error: "not_subscribed"`), так
  что обойти проверку одним лишь открытием Mini App нельзя.

**Обязательно добавьте бота в канал** (хотя бы участником; для закрытых
каналов — администратором), иначе Telegram Bot API не даст боту узнать
статус подписки пользователя — в этом случае проверка **не блокирует**
пользователей технической ошибкой (fail-open), а просто пропускает их,
залогировав предупреждение. Проверьте у себя, что всё настроено правильно,
прежде чем полагаться на эту защиту.

## Установка

Для продакшен-сервера (Ubuntu/Debian) проще всего использовать `install.sh` — см.
раздел «Автоустановка (install.sh)» выше. Ниже — вариант для локальной разработки/теста
и ручная установка без скрипта.

### 1. Подготовка

- Создайте бота через [@BotFather](https://t.me/BotFather), получите `BOT_TOKEN`.
- Включите **Telegram Stars** для бота (в @BotFather ничего доп. включать не
  нужно — это встроенная валюта, работает сразу для любого бота).
- В @BotFather настройте Mini App: `/newapp` или `/mybots → Bot Settings →
  Menu Button` и укажите URL Mini App — **`<WEBAPP_URL>/tgapp`** (не просто домен,
  а именно с `/tgapp` — на корне теперь публичный веб-магазин, см. таблицу выше).
- На каждом сервере с 3x-ui создайте нужные инбаунды (VLESS+Reality
  рекомендуется), включите **Subscription Settings** (Panel Settings →
  Subscription) и сгенерируйте API-токен (Settings → Security → API Token).
  Эти данные впишите либо в `.env` (для первой панели — «бутстрап»), либо
  сразу добавьте панель через админку `/admin` → «Серверы».

### 2. Конфигурация

```bash
cp .env.example .env
# заполните BOT_TOKEN, WEBAPP_URL, XUI_* переменные
```

### 3. Запуск локально (без Docker)

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# два процесса в отдельных терминалах:
python -m bot.main
uvicorn webapp.main:app --host 0.0.0.0 --port 8000
```

Для теста Mini App нужен HTTPS-домен — быстрее всего через `ngrok http 8000`
или `cloudflared tunnel --url http://localhost:8000`, полученный URL (без
`/tgapp`) пропишите в `WEBAPP_URL`, а в настройках Mini App у @BotFather — этот
же URL с `/tgapp` на конце.

### 4. Запуск через Docker

```bash
docker compose up -d --build
```
(добавьте свой reverse-proxy/HTTPS перед сервисом `webapp`, например через
Caddy/Nginx + Let's Encrypt — либо используйте `install.sh` на хосте вместо
Docker, если устраивает нативная установка с systemd).

## Автоустановка (install.sh)

Скрипт `install.sh` в корне репозитория разворачивает проект на чистом
Ubuntu/Debian-сервере одной командой:

```bash
git clone <ваш форк этого репозитория>
cd <папка проекта>
sudo bash install.sh
```

Что он делает:

1. Ставит системные зависимости: `python3`, `python3-venv`, `nginx`, `certbot` +
   `python3-certbot-nginx`, `git`, `sqlite3`.
2. Проверяет версию Python (нужен 3.10+ — есть по умолчанию в Ubuntu 22.04/24.04 и
   Debian 12; на более старых системах скрипт остановится с понятной ошибкой).
3. Интерактивно спрашивает: домен, email для Let's Encrypt, токен бота, логин/пароль
   админки (пароль можно не вводить — тогда сгенерируется случайный и будет показан
   один раз в конце), данные первой панели 3x-ui (можно пропустить и добавить позже
   через админку), данные ЮKassa (можно пропустить), обязательный канал (можно
   пропустить), username бота для ссылки на сайте. `SECRET_KEY` генерируется
   автоматически.
4. Пишет `.env`, создаёт отдельного системного пользователя `vpnshop` (без права
   логина), python-окружение в `.venv` и ставит зависимости из `requirements.txt`.
5. Создаёт два systemd-сервиса — `vpnshop-bot` (бот) и `vpnshop-web` (uvicorn,
   слушает только `127.0.0.1`) — включает и запускает их.
6. Настраивает nginx как reverse proxy на `127.0.0.1:8000` для указанного домена.
7. Проверяет, что DNS домена уже указывает на этот сервер, и выпускает бесплатный
   HTTPS-сертификат через `certbot --nginx` (автопродление ставится самим certbot,
   отдельно ничего настраивать не нужно).

В конце скрипт печатает адреса всех трёх разделов сайта, логин/пароль админки (если
создавались) и чек-лист следующих шагов (URL для Menu Button в BotFather, webhook
ЮKassa, добавление панели/бота в канал, если не сделали это в процессе).

Скрипт безопасно перезапускать повторно — если найдёт уже существующий `.env`,
спросит, использовать ли его без вопросов (полезно, чтобы просто пересоздать
сервисы/nginx-конфиг после обновления кода через `git pull`).

**Важно:** скрипт делает `chown -R` всего каталога проекта на системного
пользователя `vpnshop` — если планируете и дальше `git pull` в этой же папке,
делайте это от `root`/`sudo`, либо явно от имени `vpnshop`
(`sudo -u vpnshop git pull`), иначе получите ошибки доступа.

Для не-Ubuntu/Debian систем (CentOS, Alpine и т.п.) настройте эквиваленты
вручную по аналогии со скриптом: venv + systemd (или любой supervisor) +
nginx/Caddy + certbot, либо используйте Docker (`docker-compose.yml`).

Команды для администрирования из консоли
Обновление кода
После `git push` в свой репозиторий — на сервере одна команда вместо
`git pull` + переустановки зависимостей + `chown` + рестарта вручную:
```bash
sudo bash /opt/<папка-проекта>/update.sh
```
(`update.sh` лежит в корне репозитория — делает `git pull`, ставит
обновлённые зависимости, возвращает файлам владельца `vpnshop` и
перезапускает оба сервиса.)
Сервисы (бот и веб)
```bash
systemctl status vpnshop-bot vpnshop-web      # статус обоих
systemctl restart vpnshop-bot vpnshop-web     # перезапуск обоих
systemctl stop vpnshop-web                    # остановить (например, для техработ)
journalctl -u vpnshop-bot -f                  # логи бота в реальном времени (Ctrl+C — выйти)
journalctl -u vpnshop-web -f                  # логи веб-сервиса в реальном времени
journalctl -u vpnshop-web -n 100 --no-pager   # последние 100 строк без live-режима
```
База данных (SQLite)
БД лежит в `<папка-проекта>/vpnshop.db`. Удобные запросы
(`-header -column` — красивый вывод таблицей):
```bash
cd /opt/<папка-проекта>

# Активные Telegram-подписки
sqlite3 -header -column vpnshop.db "SELECT id, user_id, expires_at, is_active FROM subscriptions WHERE is_active=1 ORDER BY expires_at;"

# Активные подписки с сайта (веб-магазин)
sqlite3 -header -column vpnshop.db "SELECT id, email, expires_at, is_active FROM web_subscriptions WHERE is_active=1 ORDER BY expires_at;"

# Последние 20 платежей
sqlite3 -header -column vpnshop.db "SELECT id, user_id, email, amount, currency, provider, status, created_at FROM payments ORDER BY id DESC LIMIT 20;"

# Список тарифов
sqlite3 -header -column vpnshop.db "SELECT id, title, duration_days, price_stars, price_rub, is_active FROM plans;"

# Список подключённых панелей 3x-ui
sqlite3 -header -column vpnshop.db "SELECT id, name, base_url, is_primary, is_active FROM panels;"

# Сколько всего пользователей бота
sqlite3 vpnshop.db "SELECT COUNT(*) FROM users;"
```
Через саму админку (`/admin`) то же самое обычно удобнее — эти запросы
больше для быстрого «подглядеть» без браузера.
Бэкап базы
Копировать файл `.db` "на живую" рискованно (может зацепить середину
записи) — лучше через встроенный `.backup`:
```bash
mkdir -p /opt/backups
sqlite3 /opt/<папка-проекта>/vpnshop.db ".backup '/opt/backups/vpnshop-$(date +%F).db'"
```
Автоматически раз в сутки — добавить в cron:
```bash
crontab -e
# и добавить строку:
0 3 * * * sqlite3 /opt/<папка-проекта>/vpnshop.db ".backup '/opt/backups/vpnshop-$(date +\%F).db'"
```
nginx и сертификат
```bash
nginx -t                          # проверить конфиг перед reload
systemctl reload nginx            # применить изменения без разрыва соединений
certbot certificates              # какие сертификаты есть и когда истекают
certbot renew --dry-run           # проверка, что автопродление сработает (без реального продления)
```
Автопродление уже настроено самим certbot (systemd timer) — руками
обычно ничего делать не нужно.
Полезное при отладке
```bash
curl -sI https://ваш-домен/                  # быстро проверить, что сайт живой
curl -s http://127.0.0.1:8000/admin/api/me   # проверка, что API отвечает в обход nginx
ss -tlnp | grep :8000                        # что слушает порт 8000 (должен быть uvicorn)
df -h                                        # место на диске (SQLite + логи иногда разрастаются)


## Оплата картой через ЮKassa

Поддержаны два способа оплаты одновременно: Telegram Stars (всегда доступен)
и банковская карта через ЮKassa (появляется в Mini App автоматически, как
только заполнены переменные окружения).

1. Зарегистрируйте магазин на [yookassa.ru](https://yookassa.ru), в личном
   кабинете возьмите `shopId` и `secretKey` (Настройки → API) и впишите их в
   `.env` (`YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`).
2. В личном кабинете ЮKassa включите HTTP-уведомления (webhooks) и укажите
   URL: `https://ваш-домен/api/yookassa/webhook`, события —
   `payment.succeeded` и `payment.canceled`.
3. У каждого тарифа (`core/database.py`, поле `price_rub`) должна быть задана
   ненулевая цена в рублях — иначе оплата картой для этого тарифа будет
   недоступна.
4. Готово: во вкладке «Тарифы» рядом с оплатой Stars появится кнопка «💳
   Банковская карта». Пользователь оплачивает на странице ЮKassa (открывается
   через `Telegram.WebApp.openLink`, поддерживает 3-D Secure), после оплаты
   ЮKassa шлёт вебхук на бэкенд, который **дополнительно сверяет статус
   платежа прямым запросом к API** (тело вебхука не считается доверенным
   само по себе) и затем создаёт/продлевает клиента в 3x-ui и уведомляет
   пользователя сообщением от бота.

Тот же вебхук (`POST /api/yookassa/webhook`) обслуживает и заказы с публичного
веб-магазина (`/`, без Telegram) — по полю `kind` в метаданных платежа
(`"telegram"` или `"web"`) бэкенд определяет, в какую таблицу
(`Subscription` или `WebSubscription`) записать результат. Настраивать
webhook в ЮKassa нужно только один раз — он общий для обоих сценариев.

Важно: если база данных (`vpnshop.db`) уже была создана до обновления (без
поля `price_rub` в таблице `plans`), удалите файл `vpnshop.db` перед первым
запуском после этого изменения — `create_all` не делает автоматических
миграций для уже существующих таблиц. В продакшене для таких изменений
стоит использовать Alembic.

## Веб-магазин без Telegram

На корне домена (`/`) — обычный сайт: тарифы, поле email, оплата картой через
ЮKassa, страница результата с QR-кодом и ссылкой-подпиской сразу после оплаты
(`webapp/static/shop/`). Он не требует ни Telegram Stars (для сайта работает
только оплата картой), ни авторизации через `Telegram.WebApp.initData` —
вместо Telegram user id покупатель идентифицируется по email
(`core.database.WebSubscription`, отдельная таблица от Telegram-подписок).

Особенности:

- Тарифы на сайте — только те, у которых заполнена цена в рублях
  (`GET /shop/api/plans` фильтрует `price_rub > 0`); тарифы без цены в
  рублях там просто не показываются.
- Повторная покупка с тем же email продлевает существующую веб-подписку
  (аналогично тому, как это работает для Telegram-пользователей).
- Email нигде не используется для отправки писем — в проекте нет
  интеграции с email-рассылкой (SMTP), ссылка-подписка показывается только
  на странице результата оплаты. Если нужно продублировать её на почту —
  добавьте отправку письма в `webapp/api/shop.py` (например, через
  SMTP-библиотеку или API стороннего почтового сервиса) в месте, где
  вебхук помечает платёж оплаченным.
- Управляется из той же админки: вкладка «🌐 Веб-магазин» — список покупок
  по email, ручное продление и включение/выключение (аналогично разделу
  «Пользователи» для Telegram).
- Требует, чтобы ЮKassa была настроена (`YOOKASSA_SHOP_ID`,
  `YOOKASSA_SECRET_KEY`) — без них раздел «Купить» на сайте вернёт ошибку.
- Ссылка на бота на сайте (кнопка «Открыть в Telegram») задаётся через
  `SHOP_BOT_URL`; название сайта — через `SHOP_TITLE`.

## Тарифы

Тарифы по умолчанию создаются автоматически при первом запуске (см.
`core/database.py::init_models`). Дальше их удобно редактировать прямо в
веб-админке (`/admin` → «Тарифы»).
